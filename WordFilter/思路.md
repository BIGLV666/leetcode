# 745. 前缀和后缀搜索

## 题目描述

构造时给定一批单词 `words`（下标从 0 到 n-1），之后会反复调用查询函数
`f(pref, suff)`：

```text
f(pref, suff) = 所有「以 pref 开头 且 以 suff 结尾」的单词中,下标的最大值
                若没有这样的单词,返回 -1
```

题目链接:[745. 前缀和后缀搜索](https://leetcode.cn/problems/prefix-and-suffix-search/)

数据规模(决定了我们必须优化查询):

```text
1 <= words.length <= 15000
1 <= words[i].length <= 10
f 最多被调用 15000 次
```

### 示例

```text
输入:["WordFilter","f"]
      [[["apple"]], ["a","e"]]
输出:[null, 0]
```

只有 `apple`(下标 0)以 `a` 开头、以 `e` 结尾,答案为 0。

---

## 方法一:双 Trie + 子树收集(直观,但会超时)

这是仓库里 `WordFilter.java` 的写法,先讲它,因为它是理解方法二的跳板。

### 结构

建两棵 Trie:

```text
前缀 Trie:正常插入每个单词     -> 每个节点代表「某个单词的前缀」
后缀 Trie:把单词倒过来插入     -> 每个节点代表「某个单词的后缀」
```

每个单词的**结尾节点**记 `isEnd = true` 和 `index = 单词下标`。

### 查询流程

```text
① 沿前缀 Trie 走 pref:
     走不通 -> 没有单词以 pref 开头,返回 -1
     走到节点 node
② DFS 收集 node 整棵子树里所有 isEnd 节点的下标,放进集合 set
     (子树里的每个 isEnd 节点,都对应一个「以 pref 开头」的单词)
③ 沿后缀 Trie 倒着走 suff(注意后缀 Trie 存的是倒序单词):
     走不通 -> 返回 -1
     走到节点 node1
④ 在 node1 的子树里 DFS,找「下标在 set 中」的最大者返回
```

### 为什么慢

第 ②、④ 步每次查询都要**遍历整棵子树**。最坏情况下(比如所有单词都以
`a` 开头),一次查询就要访问约 15 万个节点,还要配大量 HashMap 操作:

```text
15000 次查询 × 15 万节点 ≈ 22.5 亿次操作   ->  实测 18.8 秒,超时
```

问题出在:**每次查询都在重复劳动**——同样的 `(pref, suff)` 组合,答案其实只跟这两个
字符串有关,跟查询本身无关,但我们每次都重新搜一遍。

方法二就是把这份劳动**一次性在构造时做完**。

## 方法二:预处理全部 (前缀, 后缀) 组合 + 排序 + 二分

这是 `WordFilterFast.java` 的写法。整体分四步:

```text
构造:① 建前缀 Trie,沿路记录每个长度的节点编号
     ② 建后缀 Trie(插倒序单词),沿路记录每个长度的节点编号
     ③ 枚举每个单词的「全部 (前缀, 后缀) 组合」,连同词下标打包成一个 long
     ④ 把所有 long 排序
查询:① 前缀 Trie 走 pref  -> 得到编号 a
     ② 后缀 Trie 倒走 suff -> 得到编号 b
     ③ 用 (a, b) 二分查表,取该组里最大的词下标
```

下面逐步展开。

---

### 第 1 步:核心观察——一个单词能回答的查询只有 (L+1)² 种

一个长度为 `L` 的单词 `w`,能被哪些查询命中?

```text
前缀可以是: w[0..0], w[0..1], ..., w[0..L-1], 以及空串      共 L+1 种
后缀可以是: w[L-1..], w[L-2..], ..., w[0..], 以及空串        共 L+1 种
```

两两组合,共 `(L+1)²` 种。比如 `w = "ab"`(L=2)能回答的 9 种查询:

```text
前缀: ""    "a"    "ab"
后缀: ""    "b"    "ab"
组合: ("", ""), ("", "b"), ("", "ab"), ("a", ""), ("a", "b"),
      ("a", "ab"), ("ab", ""), ("ab", "b"), ("ab", "ab")
```

关键结论:**每个组合的答案至少是 w 自己的下标**(w 就是满足该查询的一个词)。

所以构造时把「每个单词 × 它的每个 (前缀, 后缀) 组合」全部枚举出来,记下
"该组合的答案至少是下标 i";同一个组合被多个单词贡献时,取最大的下标即可。

数量估算:

```text
Σ (L+1)² <= 15000 × 11² = 15000 × 121 ≈ 181.5 万 条记录
```

一个 `long` 数组(每条 8 字节,约 14.5 MB)就能装下。

> 注意:前缀和后缀**允许重叠**。比如 `w = "aba"`,查询 `(pref="ab", suff="ba")`
> 也是合法的。所以枚举时 `p`(前缀长度)和 `j`(后缀起点)各自独立取遍
> `0..L`,不加 `p + 后缀长度 <= L` 之类的限制。

---

### 第 2 步:用 Trie 节点编号代替字符串

记录里要存「前缀字符串」和「后缀字符串」。直接存 String 既慢又占内存。

技巧:**Trie 的节点编号天然就是字符串的唯一编号**。

- 同一个字符串在 Trie 里只会对应一个节点(公共前缀被合并);
- 不同字符串路径不同,节点编号必然不同;
- 于是「前缀字符串」可以换成「前缀 Trie 里的节点编号」,后缀同理。

这样记录就从「三元组 (String, String, int)」变成「纯整数三元组
(前缀编号, 后缀编号, 词下标)」。

**编号是怎么来的**(构造第 ①② 步):

```text
前缀 Trie 从 1 号节点(root)开始,每新建一个节点编号 +1。
插入单词 w 时沿路走:走第 p 个字符之前编号记为 prefIds[p],
走完 p 个字符后 prefIds[p+1] 就是「w 的长度 p+1 前缀」的编号。

  prefIds[0] = 1          -> 空前缀
  prefIds[p+1] = ...      -> w[0..p] 的编号

后缀 Trie 插入的是「倒序的单词」:
  倒序单词的长度 t 前缀 = 原单词的长度 t 后缀(倒着写)。
  所以插入 reverse(w) 沿路记下的 revIds[t] 正好是「w 的长度 t 后缀」的编号。

  revIds[0] = 1           -> 空后缀
  revIds[t] = ...         -> w[L-t..L-1] 的编号
```

查询时同理:沿前缀 Trie 正向走 `pref` 得到编号 `a`;沿后缀 Trie **倒着喂**
`suff` 的字符(因为后缀 Trie 的路径拼出来是倒序串)得到编号 `b`。

为什么查后缀要把字符倒着喂?后缀 Trie 里,路径 `c -> b -> a` 拼出来是 `"cba"`,
它代表原单词的后缀 `"abc"`。所以要查 "以 abc 结尾",就得按 `c, b, a` 的顺序走。

Trie 节点的插入与分配(`child` 方法):

```java
private static int child(int[][] next, int cur, char c, int[] nextId) {
    int slot = c - 'a';
    if (next[cur][slot] == 0) {     // 0 表示这个孩子还不存在
        next[cur][slot] = nextId[0]++;   // 分配一个新编号(从 2 开始,1 是 root)
    }
    return next[cur][slot];
}
```

这里用 `int[] nextId` 而不是 `int`,是因为 Java 的 int 传参是值拷贝,
数组才是可变引用,方便在静态方法里"顺手"分配编号。

节点数上限:Trie 的节点数 <= 1 + 插入的总字符数(每插入一个字符,最多多一个新节点)。

```text
总字符数 <= 15000 × 10 = 150000  ->  每棵 Trie 节点数 <= 150001
代码里 cap = totalChars + 2(编号从 1 开始,再多留 1 个余量)
```

### 第 3 步:long 的位划分(逐位拆解)

一条记录是三元组 `(前缀编号 a, 后缀编号 b, 词下标 i)`。三个数能塞进一个 64 位
`long`,各分一段:

```text
bit  63..............................0
     [ 50..63 空 ][ 32..49 前缀编号 ][ 31..14 后缀编号 ][ 13..0 词下标 ]
                  <--- 18 bit --->  <--- 18 bit -->  <--- 14 bit -->
```

对应的三个常量:

```java
INDEX_BITS  = 14;                        // 词下标占低 14 位
INDEX_MASK  = (1L << 14) - 1;            // 0b11111111111111 = 16383,取低 14 位的掩码
SUFF_SHIFT  = 14;                        // 后缀编号从 bit 14 开始放
PREF_SHIFT  = 32;                        // 前缀编号从 bit 32 开始放
```

各字段需要多少位:

```text
词下标:   最大 15000 - 1 = 14999 < 2^14 = 16384      -> 14 bit 够
节点编号: 最大 150001 < 2^18 = 262144                -> 18 bit 够
合计:     14 + 18 + 18 = 50 bit < 64                 -> 一个 long 装得下
```

打包与拆解:

```java
// 打包(构造时)
long record = ((long) a << PREF_SHIFT)   // 前缀编号左移 32 位,落在 bit 32..49
            | ((long) b << SUFF_SHIFT)   // 后缀编号左移 14 位,落在 bit 14..31
            | i;                         // 词下标直接占低 14 位

// 拆解(查询后取答案)
int wordIndex = (int) (record & INDEX_MASK);   // 与掩码按位与,只留低 14 位
```

移位的直观理解:把三个数当成三段"行程编码",`<< 32` 相当于把前缀编号
乘以 2³²,腾出低 32 位给后缀编号和下标;按位或 `|` 就是把三段无缝拼起来
(因为各段互不重叠,或运算等价于拼接)。

为什么前缀编号要放到 bit 32 而不是紧跟在后缀编号后面(bit 32 = 14 + 18)?
这不是硬性要求,只要满足

```text
SUFF_SHIFT + 18 <= PREF_SHIFT   且   PREF_SHIFT + 18 <= 64
```

即可。放 32 是为了对齐好看、且位预算非常宽裕(最高还剩 14 位空闲,
即使节点编号超出预期也不至于溢出)。

### 第 4 步:排序——让"同一个查询"的记录连成一串

把所有记录按 `long` 的**数值升序**排序(`Arrays.sort(pairs)`)。
排序键的比较顺序是从高位到低位:

```text
先比前缀编号(bit 32..49)
  相同再比后缀编号(bit 14..31)
    再相同则比词下标(bit 0..13)
```

于是排序后的数组有这样的结构:

```text
[ (a1,b1,*) ... (a1,b1,*) | (a1,b2,*) ... | ... | (a2,b1,*) ... ]
  \______ 组1: (a1,b1) ____/\_ 组2: (a1,b2) _/       \_ (a2,b1) _/
```

**同一个 (前缀编号, 后缀编号) 的所有记录在数组里是连续的一段**(称为一个"组"),
而且组内按词下标升序——因为组内前两段完全相同,能比较的只剩低 14 位的词下标。

所以:

```text
查询 (a, b) 的答案 = 该组最后一条记录的词下标
```

不需要额外去重:同一组合即使被多个单词贡献(包括重复单词、不同单词),
它们都在同一组里,组内最大的下标自然排在最后。

### 第 5 步:查询流程(逐步)

```java
public int f(String pref, String suff) {
    /* ① 正向走前缀 Trie,拿到 pref 的编号 */
    int a = 1;                                      // 1 号是 root,代表空前缀
    for (int i = 0; i < pref.length(); i++) {
        a = prefNext[a][pref.charAt(i) - 'a'];
        if (a == 0) {
            return -1;                              // 0 = 没有这条路 -> 没词以 pref 开头
        }
    }

    /* ② 倒序走后缀 Trie,拿到 suff 的编号 */
    int b = 1;
    for (int i = suff.length() - 1; i >= 0; i--) {  // 注意 i 从最后一个字符开始
        b = suffNext[b][suff.charAt(i) - 'a'];
        if (b == 0) {
            return -1;
        }
    }

    /* ③ 二分查表 */
    long key = ((long) a << PREF_SHIFT) | ((long) b << SUFF_SHIFT);  // 低 14 位为 0
    int lo = lowerBound(key);                       // 第一条 >= key 的位置(组起点)
    int hi = lowerBound(key + INDEX_MASK + 1);      // 第一条 >= key+16384 的位置(组终点)
    return lo < hi ? (int) (pairs[hi - 1] & INDEX_MASK) : -1;
}
```

逐条解释:

**① 前缀编号**。空串的编号就是 root(1):循环一次都不执行,`a` 保持 1,
正好对应枚举时 `p = 0` 的空前缀。走到 0 表示这条路在 Trie 里不存在——
Trie 的节点只会在"某个插入单词的路径"上被创建,所以 0 等价于
"没有任何单词以 pref 开头"。

**② 后缀编号**。同理,空后缀时 `b = 1`。循环倒着走是因为后缀 Trie 存的是
倒序单词(见第 2 步)。

**③ 二分**。这里是最绕的地方,拆开看:

一个组内的所有记录,前缀编号和后缀编号都等于 `(a, b)`,只有低 14 位的词下标
在 `0..16383` 之间浮动。所以:

```text
组内记录的取值范围是  [ key,  key + 16383 ]        (16383 = INDEX_MASK)
下一组的记录从     >= key + 16384               开始(下一组的 b 至少 +1,低 14 位又从 0 起)
```

于是:

```java
int lo = lowerBound(key);                    // 组内第一条(如果组存在,一定 >= key)
int hi = lowerBound(key + 16384);            // 组外第一条(>= key+16384 的第一条)
```

`lo` 到 `hi` 之间就是这个组的全部记录。两种情况:

```text
lo == hi  ->  没有任何记录落在 [key, key+16384) -> 没有单词能同时满足 (a,b) -> -1
lo <  hi  ->  组内有记录,取最后一条 pairs[hi-1]:
              组内按词下标升序,最后一条下标最大 -> 答案
```

`lowerBound` 是标准的"找第一个 >= key 的位置"二分:

```java
private int lowerBound(long key) {
    int lo = 0, hi = pairs.length;      // 搜索区间 [lo, hi)
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;      // 无符号右移一位,等价于 (lo+hi)/2 且防溢出
        if (pairs[mid] < key) {
            lo = mid + 1;               // mid 太小,答案在右半边
        } else {
            hi = mid;                   // mid 可能就是答案,收缩右边界(注意不写 hi = mid - 1)
        }
    }
    return lo;                          // 循环结束时 lo == hi,即第一个 >= key 的下标
}
```

两个细节:

- `(lo + hi) >>> 1` 用无符号右移而不是 `/ 2`,是为了避免 `lo + hi` 溢出成负数;
- 找到 `>= key` 的元素时不能排除它自己,所以是 `hi = mid` 而不是 `hi = mid - 1`
  ——这是 lower_bound(找下界)与普通二分查找最大的区别。

### 完整算例

用 `words = ["ab", "aa"]` 走一遍(实际代码里两棵 Trie 的编号是独立分配的,
下面也分开标注):

```text
前缀 Trie(root=1):
  插入 "ab"(i=0): 'a' -> 2, 'b' -> 3        prefIds = [1, 2, 3]
  插入 "aa"(i=1): 'a' -> 2, 'a' -> 4        prefIds = [1, 2, 4]
  节点含义: 2 = "a", 3 = "ab", 4 = "aa"

后缀 Trie(root=1,插入倒序单词):
  插入 reverse("ab") = "ba"(i=0): 'b' -> 2, 'a' -> 3
  插入 reverse("aa") = "aa"(i=1): 'a' -> 4, 'a' -> 5
  节点含义: 2 = 后缀 "b", 3 = 后缀 "ab", 4 = 后缀 "a", 5 = 后缀 "aa"
```

枚举记录(前缀编号, 后缀编号, 词下标):

```text
i=0, "ab":  (1,3,0) (1,2,0) (1,1,0)     空前缀 × {后缀 "ab","b",""}
            (2,3,0) (2,2,0) (2,1,0)     前缀 "a"
            (3,3,0) (3,2,0) (3,1,0)     前缀 "ab"
i=1, "aa":  (1,5,1) (1,4,1) (1,1,1)
            (2,5,1) (2,4,1) (2,1,1)
            (4,5,1) (4,4,1) (4,1,1)
```

查询三个例子:

```text
f("a", "a"):  a = 2(前缀 "a"),b = 4(后缀 "a")
              组 (2,4) 只有 (2,4,1)  ->  答案 1     ("ab" 不以 a 结尾)

f("a", ""):   a = 2,b = 1(空后缀)
              组 (2,1) 有 (2,1,0) 和 (2,1,1),升序排最后的是 1  ->  答案 1

f("ab","ab"): a = 3,b = 3
              组 (3,3) 只有 (3,3,0)  ->  答案 0

f("a", "x"):  b = 0(后缀 Trie 里没有 'x' 这条路)  ->  直接 -1,不用查表
```

## 正确性分析

1. **枚举覆盖所有可命中的查询**:一个单词能回答的查询组合前面已穷举为
   `(L+1)²` 种,查询若能被 w 命中,其 (前缀, 后缀) 一定在枚举范围内;
2. **取最大下标**:答案要求的正是最大下标,组内排序后取最后一条即可;
3. **重复单词**:同一单词出现多次时,每次插入都会贡献一组记录,下标更大的
   那组排得靠后,组内最后一条就是它——无需特殊处理;
4. **空前缀 / 空后缀**:`prefIds[0] = revIds[0] = 1`(root),枚举时 `p = 0`
   和 `j = L` 的组合就是空串,查询空串时循环不执行、直接用 root 编号,
   两边一致;
5. **前缀后缀可重叠**:枚举时 `p` 与 `j` 相互独立,没有做"不重叠"限制,
   与题意一致。

## 复杂度

设 n 个单词、总长 `S = ΣL`、记录数 `P = Σ(L+1)²`:

### 方法一(双 Trie + 子树收集)

```text
构造:O(S)
查询:最坏 O(整个 Trie 的节点数) ≈ O(S)      <- 15000 次 × 15 万节点,超时
空间:O(S)
```

### 方法二(预处理 + 二分)

```text
构造:O(S + P log P)      P ≈ 181.5 万,P log P ≈ 3800 万次比较
查询:O(|pref| + |suff| + log P)   ≈ 走 Trie O(20) + 二分 O(21),近乎 O(1)
空间:O(S + P)            两棵 Trie 约 2 × 150001 × 26 个 int ≈ 31 MB
                          pairs 约 181.5 万 × 8 字节 ≈ 14.5 MB
实测(15000 词 × 长度 10 × 15000 次查询):构造 0.10s,查询 0.02s,内存 52MB
```

用"构造慢一点"换"查询极快",在 n 和查询次数都很大的场景下是标准取舍。

## 易错点

### 1. 后缀查询时忘记把字符倒着喂

后缀 Trie 存的是倒序单词,查询必须从 suff 的最后一个字符开始走;
正着走会查到完全错误的后缀编号。

### 2. 枚举时漏掉空前缀 / 空后缀

`p = 0` 与 `j = L` 的组合(空串)是合法查询,漏掉后 `f("a", "")` 这类查询会
错误地返回 -1。

### 3. 前缀与后缀重叠的查询

`f("ab", "ba")` 对单词 `"aba"` 是合法命中(前缀和后缀共用中间的字母)。
枚举时若加了"前缀长度 + 后缀长度 <= L"的限制就会漏。

### 4. 二分写成了 `hi = mid - 1`

lower_bound 找的是"第一个 >= key 的位置",命中时不能排除当前元素,
必须 `hi = mid`;写成 `hi = mid - 1` 会漏掉边界。

### 5. 组的右边界算错

右边界是 `lowerBound(key + INDEX_MASK + 1)`,即 `key + 16384`;
写成 `key + 1` 会把同组里下标更大的记录排除在外,返回错误答案。

### 6. 提交时类名没改

提交 LeetCode 时要改回来。

## 总结

```text
方法一:双 Trie + 每次查询遍历子树            查询 O(S),会超时
方法二:构造时枚举 (L+1)² 组合,排序 + 二分   查询 O(log P),近乎 O(1)
```

方法二的三个关键转化:

```text
① 查询答案只由 (pref, suff) 决定  ->  可以离线预处理
② 字符串 -> Trie 节点编号          ->  记录全整数化,可打包进 long
③ 打包后排序 -> 同组连续且组内下标升序 ->  一次二分取组尾即答案
```

位运算部分记住三句话:

```text
<< 32 / << 14 是"腾位置",| 是"拼接"(各段互不重叠时等价于相加)
& INDEX_MASK 是"只留低 14 位",用来取出词下标
key + 16384 是"下一组的起点",用它做二分上界就能圈出整个组
```
